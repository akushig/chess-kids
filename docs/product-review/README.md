# 어린이체스 전체 진단과 완성 방향

검토일: 2026-10-24~25 · 기준 커밋: `8b1c68d` · 검토 당시 미추적 스킨 이미지 유지

**이 앱의 우선 과제는 콘텐츠를 더 많이 만드는 것이 아니라, 플레이 결과를 신뢰할 수 있게 하고, 막혀도 스스로 계속할 수 있게 만드는 것이다.** 이미 모험·나이트 투어·대전에 즐길 동기가 있다. 이를 공통 규칙, 도움 방식, 진행 구조로 연결하면 어린이부터 어른까지 즐기는 앱으로 발전시킬 수 있다.

현재는 귀여운 외형과 개별 기능은 있지만, “어떤 행동이 가능한가 → 왜 이 결과가 나왔는가 → 이제 무엇을 할 수 있는가”의 연결이 약하다. 일부는 UX 문제가 아니라 실제 콘텐츠 오류다. 사용자가 보고한 짜증과 도움 요청을 모두 아이의 이해력이나 난이도 문제로 해석해서는 안 된다.

## 1. 범위와 판단의 확실성

검토 범위는 홈, 모험 48단계, 퍼즐 12문제, 나이트 투어 3크기, 서바이벌 4단계, 수집 5단계, 폭탄 5단계, 디펜스 4단계, 컴퓨터 5난이도, 사람 대전, 보상·7종 스킨, 저장, PWA, 공통 렌더링·애니메이션이다. 총 81개 고정 문제·단계·크기 설정을 목록화했다. 81개가 서로 비슷한 분량이나 검증 수준이라는 뜻은 아니다.

방법과 한계:

| 방법 | 실제 확인한 것 | 범위 밖 |
|---|---|---|
| 소스 검토 | 전체 게임 모듈, 화면 생성, 데이터, AI·솔버, CSS·스킨 구조·PWA | 모든 SVG의 미술적 품질에 대한 화면 판정 |
| Node VM에서 현재 로직 실행 | 모험 48개, 수집 5개, 폭탄 5개 최단경로 계산 및 실제 클릭 핸들러 재생, 룩 실패 상태, 나이트 3크기 완주 경로 | 실제 브라우저 이벤트·애니메이션 타이밍·터치 |
| 별도 python-chess 검증 | 퍼즐 12개의 초기 국면, 지정 수의 합법성, 목표 달성, 2수 문제의 모든 첫 상대 응수 | 표준 체스 엔진 전체에 대한 인증 |
| 사용자 관찰 | 만 6세 아이의 선호, 막힘, 부모를 보고 즐기기 시작한 경험 | 다른 아이·성인의 일반적인 반응으로 단정 불가 |
| 외부 근거 확인 | FIDE 규칙, UNICEF 어린이 디지털 놀이 설계 자료 | 본 앱의 재미·교육효과를 입증한 실험은 아님 |

화면 제어는 접근 권한이 없어 실행하지 못했다. 화면 배치 문제는 렌더링 코드·CSS에 근거한 검토이며, 기기별 스크린샷 확인이나 실제 어린이 사용성 검사를 했다고 주장하지 않는다. 참고이미지 폴더는 다른 앱의 참고자료이므로 현재 앱의 실행 화면으로 사용하지 않았다.

추가로 `index.html` 순서대로 23개 스크립트를 격리된 환경에서 로드했고, 7개 스킨의 84개 기물 SVG 출력을 생성해 XML 문법을 검사했다. 이는 로딩·출력 구조 검사이며 기물 식별성이나 미술 품질의 시각 검수를 대체하지 않는다.

아래에서 **확인**은 코드·실행 결과, **가설**은 사용자 경험에 대한 해석, **설계 결정**은 앞으로 구현할 제안이다.

## 2. 먼저 보존할 강점

1. **말을 직접 움직이는 핵심 조작**이 이미 모험·대전·놀이에 통한다. 새 조작 체계보다 공통 피드백을 보강하는 편이 좋다.
2. **나이트 투어의 재도전 가치**가 실제 사용자 경험에 나타났다. 어린이를 위해 고급 도전까지 없애면 어른과 함께 즐기는 이유도 사라진다.
3. **대전 자체를 좋아한다.** 모든 학습을 끝내야 대전할 수 있게 잠그지 않는다. 대전 안에서 배우도록 돕는다.
4. **부모의 재미가 아이에게 전달된다.** 단순한 부모용 설명서보다 시범·교대·협동을 제품 기능으로 만드는 근거가 된다. 다만 이 한 사례로 효과를 일반화하지 않는다.
5. 나이트 솔버의 완주 가능/불가능/탐색 한도 구분, AI의 Worker 실행과 합법수 재확인, 친구 마주 보기, 별 최고 기록 보존은 재사용할 좋은 기반이다.
6. 별·스킨은 모으는 동기를 제공할 수 있다. 정확성과 공정성을 먼저 갖춘 후 확장한다.

### 3.1 룩 6단계: “피하라”면서 실제로는 먼저 잡아야 한다

시작 좌표는 `[3,3]`, 적 룩은 `[0,3]`, `[3,0]`이다. 좌표는 화면 좌상단 `[0,0]` 기준이다.

- 처음 이동 표시가 나오는 칸은 10개다.
- 첫 이동 후 안전한 칸은 **적 룩을 잡는 두 칸**뿐이다.
- 나머지 8개는 이동할 수 있다고 표시되지만 실제 이동 후 바로 실패한다.
- 예: `[3,3] → [3,4]`를 실행하면 `missionFailed=true`가 된다.
- 그 순간 힌트·다시 버튼이 사라진다. 안내문은 원래 “적의 공격을 피해 안전한 곳으로!”가 남는다. 보드는 입력을 무시한다.
- 지도까지 나갔다 다시 들어오면 복구되지만, 현재 화면은 그 방법을 설명하지 않는다.

**해석:** 이 단계는 단순한 룩 이동 학습에서 두 공격선과 포획을 이용한 탈출로 급격히 뛴다. 위험을 보여 주지도 않는다. 사용자가 느낀 “어른도 모르겠다”와 직접 맞닿는 문제다. 실제로 아이가 막힌 단계가 여기였는지는 별도 확인이 필요하다.

저장된 `hint`에는 룩의 대각선 이동이 들어 있지만 **현재 힌트는 BFS를 사용하므로 이 잘못된 정적 힌트가 화면에 표시되는 것은 아니다.** 데이터 정합성 결함과 현재 사용자에게 노출되는 결함을 구분해야 한다. Q-8에도 현재 사용하지 않는 잘못된 정적 힌트가 있다.

### 3.2 퍼즐 12개 전수 검증

현재 성공 판정은 목표를 달성했는지보다 `solution`에 저장된 좌표를 그대로 따랐는지를 검사한다. 마지막 저장 수를 두면 실제 체크메이트 여부와 무관하게 성공한다. 다른 합법 수를 두면 즉시 실패한다.

| 문제 | 현재 지정 해답의 결과 | 판정 |
|---|---|---|
| L1-1 | Qh8 후 흑킹이 d7/e7/f7로 피할 수 있음 | 메이트 아님 |
| L1-2 | Qd8 후 Kxd8 또는 Kf7 가능 | 메이트 아님 |
| L1-3 | Rh1→h8 경로에 흑폰 h7이 있음 | 지정 수 불법, 진행 불가 |
| L2-1 | Qh1×a8로 룩 포획 | 목표 부합 |
| L2-2 | Rd1×d5로 나이트 포획 | 목표 부합 |
| L2-3 | Bh1→c4는 대각선이 아님 | 지정 수 불법, 진행 불가 |
| L3-1 | Ng1→f3에서 지정 킹·룩 어느 것도 공격 안 함 | 포크 아님 |
| L3-2 | Qh8에서 e8 킹이 a8 룩까지의 선을 막음 | 동시 공격 아님 |
| L3-3 | Nc3→d5에서 지정 킹·룩 어느 것도 공격 안 함 | 포크 아님 |
| L4-1 | Qxg7+ Kxg7 Rh8 후 메이트 아님 | 목표 불일치 |
| L4-2 | Ra8+ 뒤 가능한 3응수 모두, Rh8 후 메이트 아님 | 목표 불일치 |
| L4-3 | Qg7+ 뒤 가능한 3응수 모두, Ra8 후 메이트 아님 | 목표 불일치 |

앱 엔진과 별도 `python-chess` 검사 결과가 일치한다. **10개는 데이터·판정 재작업 대상, 2개만 현재 명시된 목표와 해답이 부합한다.** 이는 모든 문제의 모든 가능한 수를 최적화했다는 뜻이 아니라, 앱이 정답으로 제시하는 수를 전수 검증한 결과다.

추가 문제:

- 입문 레벨 1이 체크메이트이고, 더 단순한 포획은 레벨 2다.
- 여러 수 문제의 흑 응수는 랜덤인데 백 해답은 고정 배열이다. 앞으로 올바른 문제를 넣어도 분기 처리 구조를 고치지 않으면 깨질 수 있다.
- 흑 응수 대기 중 입력 차단이 충분하지 않아 `game.turn`이 흑인 순간 흑말을 선택할 여지가 있다. 실제 브라우저 타이밍 재현은 필요하다.
- 힌트의 말 이름은 한국어 화면에서도 영어이고 좌표를 요구한다.
- 완료 목록·마지막 문제의 다음 행동·왜 맞고 틀렸는지 설명이 부족하다.

### 3.3 모험 전체: 길은 존재하지만 교육적 일관성은 부족하다

현재 규칙으로 48단계 전부 시작점에서 해결 경로가 존재하고, 저장된 `minMoves`도 최단경로와 일치했다. 이 경로를 실제 클릭 핸들러로 재생해 48개 모두 성공하는 것을 확인했다. 따라서 모험 전체가 풀 수 없는 데이터라는 진단은 틀리다. **실수 후의 회복, 개념의 순서, 실제 체스와의 연결**이 주요 문제다.

| 월드 | 주요 문제 | 권장 변화 |
|---|---|---|
| 폰 | 1·2가 사실상 같은 두 칸 전진; 6에서 장애물과 적이 같은 칸; 대각선 포획은 장애물 검사 누락으로 통과; 7의 승격 안내와 실제 변신 불일치 | 한 칸→두 칸→포획 차이; 중복 좌표 제거; 실제 승격 시범 |
| 룩 | 1수→3수 계획으로 상승; 6에서 위험 규칙이 갑자기 등장 | 방향→경로 막힘→한 번 꺾기→여러 목표; 공격선 학습은 별도 단원 |
| 나이트 | 1수 포획 후 5수 전체 포획으로 증가; 설명의 L자만으로 이해하기 어려움 | 점프 시범→1회→2회→짧은 수집; 완주는 선택 도전 |
| 비숍 | 5·6은 최단 5수, 7은 1수로 하락; 같은 색 칸 개념 학습 부족 | 같은 색의 길→장애물→반대 대각선→선택 도전 |
| 퀸 | “어디든”이 점프·비직선 이동도 가능하다는 오해 여지 | 룩+비숍 방향 결합, 길이 막히는 규칙 반복 |
| 킹 | capture 미션은 공격 검사를 하지 않음; 7의 “위협을 피하며”도 판정에 반영 안 됨 | 킹의 안전을 모든 관련 모드에서 일관되게 검사 |

폰처럼 뒤로 돌아갈 수 없는 말은 초반 선택으로 목표를 놓쳐도 명확한 막힘 감지가 없다. 사용자가 힌트를 찾아 눌러야 불가능 안내를 본다. 모험에는 한 수 되돌리기가 없다.

소스 주석의 “포크”, “체크”, “체크메이트 느낌”과 실제 목표 도달 게임은 다르다. 주석을 사용자에게 노출된 오류라고 취급할 수는 없지만, 콘텐츠 제작 기준이 아직 정리되지 않았음을 보여 준다.

### 3.4 미니게임 전체

| 콘텐츠 | 보존할 재미 | 현재 마찰 | 설계 결정 |
|---|---|---|---|
| 나이트 투어 | 공간 채우기·경로 찾기·가족이 같이 궁리 | 첫 목표부터 25칸 완주, 실패 시 전체 재시작, 모든 경로 힌트가 복잡, 점수와 실제 보상이 분리 | 주력 유지. 짧은 산책/탐험/완주로 구분, 되돌리기, 한 걸음 힌트, 같은 판 협동 |
| 서바이벌 | 움직이는 위험을 피하는 긴장 | 기다리기 가능하지만 자기 칸 표시 없음; 킹은 포획 불가; 적 행동·생성 예고 없음; 단계 통과가 게임오버 이후에야 나타남 | 안전칸 학습으로 일부 편입. 예고·공정성 검증 후 고급 생존 놀이 제공 |
| 기물 수집 | 수집과 경로 계획 | 첫 단계 무오차 8수 요구; 기물 변경·순찰·턴 제한이 한 번에 바뀜; 이름은 기물 수집인데 실제로 별 수집 | “별 모으기”로 이름 통일, 모험의 반복 가능한 공통 템플릿으로 흡수 |
| 폭탄 해제 | 순서와 제한된 수 계획 | 별 수집과 유사; 시간처럼 보이나 실제로는 이동 횟수; 3개 단계 최고 보상 불가 | 같은 템플릿의 선택 도전. 입문 추천에서 제외, 원하면 기존 폭탄 테마 유지 |
| 디펜스 | 공격·포획의 즉각적 반응, 여러 적 대응 | 남은 기회가 표시 안 됨; “끝줄 도달”과 실제 판 밖 도달 판정 불일치; 적 이동 예고 없음; 서로 겹칠 수 있음 | 주력 유지. 소수 적·예고 경로·명시된 생명·짧은 웨이브로 정리 |

나이트 투어 상세:

- 5×5·6×6·7×7 기본 시작점에서 솔버 경로를 검사했고, 중복 없이 모든 칸을 방문하는 유효한 경로다. 솔버 입력 보드도 훼손하지 않았다.
- 랜덤 시작의 해법 존재 확인과 탐색 한도 초과를 불가능과 구분하는 구현은 유지한다.
- 별이 랜덤으로 나타나며 연속 획득 점수가 있지만, 완주 불가능한 방향으로도 아이를 끌 수 있다. 별 수집 동기와 완주 목표가 경쟁한다.
- 완주 때만 별 저장 코드가 실행되므로 80% 방문 시 2별이라는 분기는 실제 도달하지 않는다. 현재 중간 성과는 저장 보상으로 연결되지 않는다.
- 갈림길 경고는 “잘 생각해봐요”라고 말하지만 어느 선택을 어떻게 비교할지 알려 주지 않는다. 고급 경고로는 쓸 수 있으나 초보 도움으로는 부족하다.

보상 검증:

| 게임·단계 | 최단 이동 | 현재 최고로 받을 수 있는 별 | 이유 |
|---|---:|---:|---|
| 수집 1 | 8 | 1 | 제한 8, 남은 턴 0 |
| 폭탄 1 | 2 | 2 | 3별 조건은 1수 이하 |
| 폭탄 3 | 6 | 1 | 3별 2수 이하, 2별 4수 이하 |
| 폭탄 5 | 5 | 2 | 3별 조건은 4수 이하 |

수집 2·3·4·5와 폭탄 2·4는 현재 최단해로 3별이 가능하다. 수집 5에는 시작 위치에 별이 있지만 시작 시 획득되지 않아 다시 돌아와야 한다.

서바이벌·디펜스에서 별도로 고칠 구현:

- 서바이벌 힌트 주석은 적 이동을 포함한 선읽기라고 하지만 실제 함수는 적을 움직이지 않고 인접 안전칸 수만 센다. 미래 안전을 보장하지 못한다.
- 서바이벌 안전 검사에서 현재 킹이 있던 칸을 비우지 않고 공격선을 계산하므로, 이동 뒤 드러나는 공격선이 하이라이트와 달라질 수 있다.
- 최고 기록을 먼저 갱신한 뒤 `turn > record`를 검사하므로 새 기록 축하 조건이 성립하지 않는다.
- 디펜스는 2회 돌파 때 실패하지만 진행 중 남은 기회가 보이지 않는다. 1회 돌파 뒤 성공해도 “모든 적을 막았어요”라고 말한다.
- 디펜스 적 이동에 점유 충돌 검사가 없고, 하단의 나이트는 전진 후보가 없어 멈출 수 있다. 적 포획·충돌·돌파 규칙을 먼저 확정해야 한다.

## 4. 대전: 상대 난이도와 이해 난이도는 다르다

오늘 추가된 5단계 AI와 친구 대전은 좋은 기반이다. 그러나 아주 약한 AI를 선택해도 **체크 규칙, 합법수 제한, 게임 종료 조건**은 쉬워지지 않는다. 아이에게 필요한 것은 상대의 실수를 더 늘리는 것만이 아니라, 자신의 수가 왜 제한되는지 보이는 환경이다.

확인한 공백:

- 체크 중인 킹·공격자·공격선 표시 없음.
- 움직일 수 없는 말을 눌러도 막힌 이유 없음. 경로 차단·체크 미해소·핀·차례를 구별해 설명하지 않음.
- 힌트, 되돌리기, 진행 중 저장, 재개, 마지막 수 표시가 없음.
- 친구 대전은 최초 기본값이 한 수 30초이며 시간이 끝나면 AI가 대신 둔다. 초보에겐 “내가 안 눌렀는데 말이 움직임”이 새로운 이해 부담이 될 수 있다.
- 승패 이후 선택은 사실상 다시 시작뿐. 방금 배운 한 장면을 놀이로 이어 주지 못한다.
- 대전은 전체 별 획득 경로에 포함되지 않는다. 좋아하는 콘텐츠가 수집 성장과 분리된다.
- 캐슬링 없음·승격 퀸 고정은 AI 주석에 명시된 현재 구현이다. 표준 체스를 기대하는 숙련자에게는 제한이다. 초보 도움과 규칙 정확성을 분리해야 한다.

보충: `ChessGame.isAttacked()`는 이동 함수를 재사용해 빈칸에 대한 폰 공격 지도를 잘못 반환한다. 현재 킹 이동 합법성은 킹을 놓은 뒤 검사하므로 **이 발견만으로 실제 대전에서 폰 체크가 전부 잘못된다고 결론 내릴 수 없다.** 다만 앞으로 위험칸 표시를 이 함수로 만들면 문제가 되므로 공격 지도와 이동 생성은 분리해야 한다.

규칙 검토 기준은 [FIDE Laws of Chess](https://handbook.fide.com/chapter/e012023)의 3.7·3.8·3.9와 종료 조항이다. 체크 상태에서 안전을 회복하는 수만 허용하고, 캐슬링·승격 선택을 포함한 표준 규칙과 앱의 간소화 여부를 구분한다. 대회용 시계·청구 절차를 모두 도입할 필요는 없지만 사용자에게 설명 없이 다른 규칙을 학습시키지는 않아야 한다.

## 5. 앱 전체를 미완성으로 느끼게 하는 공통 원인

### 메뉴와 진행

현재 홈은 모험·퍼즐·대전·미니게임을 동등한 네 메뉴로 보여 준다. 하지만 아이가 고를 때 필요한 질문은 “어제 하던 것”, “지금 재미있어 보이는 것”, “누구와 둘 것”이다. 메뉴가 제작 방식에 따라 분리되어 있고 활동 간 다음 행동을 제시하지 않는다.

퍼즐과 미니게임의 구분이 모호하다는 느낌도 타당하다. 수집·폭탄은 반복 플레이 게임이라기보다 고정된 경로 퍼즐이다. 반대로 나이트 투어는 퍼즐 성격이 강하지만 재도전 놀이로 기능한다. **내부 알고리즘이 아니라 사용 목적과 플레이 흐름으로 메뉴를 나눠야 한다.**

### 피드백과 도움

- 같은 노란색 계열이 선택·목표·이동 후보를 표현한다. 의미를 모양·동작으로도 나눌 필요가 있다.
- 전체 경로 표시가 항상 좋은 힌트는 아니다. 현재 한 행동을 이해시키기보다 답안 따라 그리기가 될 수 있다.
- 공통 힌트의 `document.querySelector('.mission-speech')`는 숨겨진 모험 화면이 남아 있으면 그쪽을 먼저 고른다. 활성 화면으로 범위를 제한해야 한다.
- 텍스트·용어 중심이고 음성 안내나 짧은 조작 시범은 없다. 읽기 수준과 체스 숙련도를 별도로 지원해야 한다.
- 잘못 누름, 규칙상 불가능, 문제의 해법을 놓침, 단순히 생각 중임에 서로 다른 대응이 필요하다.

### 저장·보상·외형

- 단일 localStorage에 기록을 합친다. 부모가 먼저 플레이하면 아이 기록과 보상이 섞인다.
- 콘텐츠를 재배열하면 배열 인덱스 기반 별 기록이 다른 문제에 연결될 수 있다. 고정 ID가 필요하다.
- 모험 최대 3별, 퍼즐 1별, 나이트는 완주 시 3별, 다른 게임은 서로 다른 계산식이다. 아이에게 공통 의미가 없다.
- 해금 스킨을 사용하려면 별 화면과 스킨 창을 스스로 찾아가야 한다. 획득 순간의 명확한 안내 연결이 없다.
- 대체 스킨도 말 종류·진영이 즉시 식별되어야 한다. 모든 테마에서 같은 기물 배지와 내 편 표시를 유지해야 한다.
- `APP_VERSION`은 4월 값인 반면 서비스워커는 v28이다. 실제 빌드 식별을 통일해야 오류 제보와 업데이트 확인이 가능하다.
- 일부 저장 함수는 쓰기 실패를 처리하지 않아 제한된 저장 환경에서 결과 처리가 끊길 가능성이 있다.

### 플랫폼·접근성·기술 기반

- 보드·칸이 클릭 가능한 `div`이며 기물/좌표/선택/가능 이동의 접근성 이름과 키보드 조작이 없다.
- 확대 제한 viewport, 반복 애니메이션, 동작 감소 설정 부재를 재검토한다.
- 보드는 최대 400px, 앱은 480px다. 태블릿·PC를 쓰는 어린이와 어른에게 공간 활용이 부족하다. 작은 휴대폰에서 8×8 칸의 실제 터치성은 실기기로 확인해야 한다.
- manifest의 설명은 “5~7세”이며 세로 방향을 선언한다. 이번 목표인 넓은 어린이 범주·성인 놀이와 맞춰 수정한다.
- 오프라인 캐시는 공룡·티니핑·로봇·배민 스킨 JS, manifest·앱 아이콘 등을 포함하지 않으며 네트워크 응답을 런타임 캐시에 넣지도 않는다.
- 서비스워커 업데이트 중 새로고침하는 흐름과 진행 저장 부재가 결합하면 판이 소실될 수 있다. 안전한 시점에 업데이트 적용이 필요하다.
- 전역 상태·DOM 전체 교체·모드별 중복 이동 구현 때문에 같은 규칙과 복구 UI가 쉽게 달라진다. 전면 프레임워크 재작성보다는 공통 규칙·세션·보드 계층부터 정리한다.
- 대전에는 늦은 콜백을 버리는 토큰이 있지만 다른 모드에는 같은 보호가 없다. 나간 화면의 팝업·힌트·AI 응수가 뒤늦게 실행되지 않는지 검증해야 한다.

## 6. 권장 완성 방향

**제품 약속: “직접 움직이며 배우고, 막혀도 도움을 받아 계속 놀며, 가족과 같은 체스를 즐긴다.”**

핵심 구조는 세 가지다.

1. **모험:** 한 가지 새 개념을 짧게 경험하고, 조금 바꾼 판에서 써 보고, 대전·놀이로 연결한다.
2. **놀이터:** 나이트 탐험과 디펜스 등 반복 자체가 즐거운 콘텐츠. 짧은 목표부터 어른용 완주·최적화까지 깊이를 제공한다.
3. **대전:** 배우며 두기·컴퓨터·가족. 규칙은 일관되게 유지하고 도움과 상대 실력을 따로 조절한다.

홈에는 “이어하기”와 지금 하기 좋은 활동 하나를 우선 보여 준다. 컬렉션과 가족 설정은 보조 위치에 둔다. 퍼즐은 모험의 상황 문제와 놀이터의 ‘한 수 발견’ 도전으로 재배치한다.

새 기능의 우선순위:

| 지금 꼭 필요 | 검증 후 확장 | 완성 1차 범위에서 보류 |
|---|---|---|
| 체크 구조대, 이유 있는 거절, 되돌리기, 한 걸음 시범, 세션 저장, 일관된 목표·결과, 공정한 보상 | 가족 협동·교대, 추천 이어하기, 작은 도전 변형, 짧은 판 대전, 프로필별 성장 | 온라인 매칭·채팅, 대규모 스토리·스킨 증설, 무제한 생성형 퍼즐, 길드·랭킹·상점 |

기능 수나 체류시간을 최우선 목표로 두지 않는다. **스스로 시작하고, 막힌 뒤 스스로 회복하고, 다음에도 자발적으로 돌아오는 경험**을 목표로 한다. 계속 플레이와 만족스럽게 그만두기 모두 지원한다.

자율성·유능감·관계·정서라는 관점은 [UNICEF RITEC Design Toolbox](https://www.unicef.org/childrightsandbusiness/workstreams/responsible-technology/online-gaming/ritec-design-toolbox)를 참고했다. 해당 프레임워크 연구는 주로 8~12세를 대상으로 하므로, 만 6세의 읽기·조작 지원에 대한 직접적인 효과 증거로 확대하지 않는다. 이 앱의 구체적인 임계값과 재미는 별도 플레이테스트로 확인한다.

다음 문서인 [DESIGN.md](DESIGN.md)에 메뉴부터 콘텐츠·상태 전이·학습 연결까지 구현 가능한 수준으로 설계했다. 실제 재미와 연령별 적합성은 구현 후 검증해야 하는 부분으로 남긴다.
